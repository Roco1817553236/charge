# 餐次重复提醒设计

## 目标

在现有“同一天、同金额”重复提醒之外，增加同日餐次重复提醒。当天餐饮中已经存在早餐、正餐或晚餐时，再保存相同餐次应先提示，但用户确认后仍可保存。

## 匹配规则

保存新增或编辑流水前，继续执行现有金额重复规则，同时执行餐次规则：

- 新流水必须是支出。
- 所选大类的当前名称必须为“餐饮”。
- 所选小类映射到餐次：
  - `早餐` → 早餐；
  - `正餐`、`午餐`、`中餐` → 正餐；
  - `晚餐` → 晚餐。
- 在同一个 `occurredLocalDate` 下查找同一餐次的未删除支出，金额、时间和备注不参与匹配。
- 编辑时排除当前流水自身。
- 历史分类已归档但仍可解析名称时继续参与；已删除且无法解析的分类不推测餐次。
- 其他大类、未细分类、零食饮料和收入不触发餐次规则。

## 合并与提示

- 金额规则和餐次规则得到的候选按流水 ID 合并，同一记录只展示一次。
- 现有弹窗和“返回检查 / 仍然保存”流程保持不变。
- 弹窗摘要根据命中原因显示：
  - 仅金额重复：现有“同一天、同金额”文案；
  - 仅餐次重复：`当天已有早餐 1 笔`；
  - 两种规则同时命中：同时说明金额和餐次风险。
- 候选列表仍最多展示 3 笔，并显示剩余数量。
- 选择返回不保存且保留草稿；选择仍然保存只放行当前提交一次。

## 架构

- 领域层提供餐次名称归一化、餐次候选匹配和两个候选集合去重函数。
- `bookStore.previewDuplicateEntry` 返回候选及命中原因，而不是仅返回流水数组。
- `App` 保存候选和原因，用于弹窗摘要；确认后的真正保存流程不再重复检查。
- 不新增 IndexedDB 字段，不修改 Transaction、Category 或 JSON schema。

## 边界与兼容

- 用户自定义“中餐”或“午餐”与默认“正餐”视为同一餐次。
- 餐次规则依赖当前分类名称；用户把餐饮或小类改为无关名称后不再触发，避免错误推断。
- 已删除流水不参与；撤销删除后重新参与。
- 日期自动递增只在最终保存成功后执行，重复弹窗本身不改变日期。

## 版本与测试

以 v1.9.0 发布。测试覆盖：

- 早餐、晚餐和正餐/午餐/中餐别名。
- 同日不同金额仍提醒，不同日期不提醒。
- 其他大类、收入、未细分类和已删除流水不提醒。
- 编辑排除自身，但与当天另一笔同餐次冲突时提醒。
- 金额与餐次候选合并去重、弹窗原因文案、返回与仍然保存。
- 手机端端到端流程及现有日期递增回归。
